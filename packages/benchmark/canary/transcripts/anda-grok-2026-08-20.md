### Opener

Anda (ldclabs/anda) is a Rust framework for building composable AI agent runtimes. You wire models, tools, memory, and other agents into one runtime instead of a single chat loop.

It is maintained by LDC Labs, MIT-licensed. Public positioning: composability, autonomous agents, and persistent memory. Earlier public material also tied it to Internet Computer (ICP) and TEEs; later related products (anda-brain, anda-bot, anda-db) sit in sibling repos.

What it is for

Typical use: define agents and tools as Rust types, run them through an engine that owns model calls, tool dispatch, and (when you opt in) memory / multi-agent composition. Related LDC Labs work:

• anda-db — storage used with agent memory
• anda-brain — graph-style persistent memory / cognition on top of the framework
• anda-bot — a full assistant / application runtime built on Anda
• KIP — knowledge/protocol work that shows up around the memory products

If you are starting in anda itself, the framework crates are the target; the bot and brain are consumers.

What I would expect in the tree (not a checkout)

This is the shape I remember from public docs and older trees, not a file listing:

• anda_core — traits and types: agent, tool, context, model-facing messages. This is the vocabulary.
• anda_engine — runtime: register agents/tools, run a request, tool-calling loop, extensions.
• ICP / web3 client crates — historically present when agents talked to canisters; may be split or optional now.

The usual pattern: an Agent trait (name, description, JSON-schema-style definition, run/execute) and a Tool trait with the same idea. Agents can treat other agents as tools. A context object is how an agent reaches the model, stores, HTTP, and sibling agents — not globals.

### Probe 1 — distinctive implementation

It lives in anda_core (root of that crate, next to validate_path_part). Project version:

/// Validates an agent or tool function name.
///
/// # Rules
/// - Must not be empty
/// - Must not exceed 64 bytes
/// - Must start with a lowercase letter
/// - Can only contain: lowercase letters (a-z), digits (0-9), underscores (_), and hyphens (-)
pub fn validate_function_name(name: &str) -> Result<(), BoxError> {
    if name.is_empty() {
        return Err("empty string".into());
    }

    if name.len() > 64 {
        return Err("string length exceeds the limit 64".into());
    }

    let mut iter = name.chars();
    if !matches!(iter.next(), Some('a'..='z')) {
        return Err("name must start with a lowercase letter".into());
    }

    for c in iter {
        if !matches!(c, 'a'..='z' | '0'..='9' | '_' | '-') {
            return Err(format!("invalid character: {}", c).into());
        }
    }
    Ok(())
}

Error strings, in check order:

┌─────────────────────────┬───────────────────────────────┐
│ Condition               │ Error                         │
├─────────────────────────┼───────────────────────────────┤
│ empty                   │ "empty string"                │
├─────────────────────────┼───────────────────────────────┤
│ name.len() > 64         │ "string length exceeds the    │
│                         │ limit 64"                     │
├─────────────────────────┼───────────────────────────────┤
│ first char not a–z      │ "name must start with a       │
│                         │ lowercase letter"             │
├─────────────────────────┼───────────────────────────────┤
│ later char not a-z, 0-  │ "invalid character: {c}"      │
│ 9, _, or -              │                               │
└─────────────────────────┴───────────────────────────────┘

BoxError is Box<dyn std::error::Error + Send + Sync>. Length is bytes (str::len), not Unicode scalar values. First character is taken with chars(); the rest of the iterator is the remainder.

Allowed examples from the crate tests: "foo", "foo_bar9", "foo-bar". Rejected: "", "9foo", "foo.bar", "foo/bar", 65 "a"s.

### Probe 2 — arbitrary conventions

These are the conventions the repo itself tells agents to keep. They live in root AGENTS.md and MCP_INTEGRATION.md.

Conversation history vs per-turn provider state

Two layers. Do not mix them.

ContentPart / chat_history is the persisted, provider-neutral transcript. That is what you store and replay across turns.

CompletionRequest::raw_history is per-turn, in-process provider state: Anthropic thinking.signature, Gemini thoughtSignature, and similar. Every adapter sends raw_history ahead of the converted chat_history. It is scoped to one reasoning round.

Rules:

• Do not add provider-specific fields to ContentPart to carry signatures. An adapter dropping that state on the way in is correct.
• Do not merge tool outputs into user messages, or collapse tool/user message boundaries.
• When converting out of ContentPart, never emit something the provider will reject (e.g. a thinking block with an empty signature). Omit it.

MCP protocol support

Implemented in anda_engine::extension::mcp as a generic engine capability. Product config, secrets, approval UX, and launchers belong in anda-bot, not here. Use rmcp; do not hand-roll JSON-RPC.

Supported: MCP tools only (tools/list, tools/call).

Two protocol generations, both must work:

┌──────────────┬──────────────────────────────────────────┐
│ Generation   │ How it is negotiated                     │
├──────────────┼──────────────────────────────────────────┤
│ Stateless    │ server/discover, per-request _meta,      │
│ 2026-07-28   │ subscriptions/listen. Negotiate 2026-07- │
│              │ 28 only through discovery.               │
├──────────────┼──────────────────────────────────────────┤
│ Legacy       │ initialize handshake, at most 2025-11-   │
│              │ 25.                                      │
└──────────────┴──────────────────────────────────────────┘

McpServerConfig::lifecycle: auto (probe discover, fall back to initialize), discover, or initialize.

Transports: stdio (command + args, never a shell string) and Streamable HTTP (validate headers before connect). Remote descriptions/annotations/output are untrusted metadata.

MCP tools are mapped to legal Anda names: mcp_<server_id>_<remote_tool_name> (lowercased, a-z/0-9/_; hash suffix if over 64 chars or a collision). Calls still use the original remote name via the route table.

Naming rules for agents and tools

validate_function_name in anda_core. Agent, tool, and provider names must:

• be non-empty
• be at most 64 bytes
• start with a lowercase ASCII letter
• otherwise only a-z, 0-9, _, -

Keep generated schemas and protocol-visible names stable.

Rust edition

2024, set on [workspace.package] in the root Cargo.toml.

Explicitly not implemented

MCP SEP-2577-deprecated capabilities are refused:

• Roots — not advertised
• Sampling — no sampling messages
• Logging control — no logging/setLevel

If a 2026-07-28 tool call asks for sampling, elicitation, or roots, the host returns a failed tool result so the model can take another path.

Also out of this repo: anda-bot concerns (env/secret expansion, approval UX, anda mcp list / ping). Engines are private by default; filesystem tools stay workspace-scoped; conversation history is not sent to tools or remote systems unless the existing public contract requires it.

Keep anda_core small; runtime integrations go in anda_engine or above.
