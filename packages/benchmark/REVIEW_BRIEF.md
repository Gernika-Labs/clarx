# Independent review brief — Clarx causal benchmark

**For:** a reviewer with no prior context on this work
**Status of the work:** Phases 1–3 built, nothing executed, nothing pre-registered
**What you are protecting:** a study whose author sells the product it evaluates

---

## Why you are being asked

This benchmark tests whether adopting Clarx — a codebase-structure standard —
causes measurable reductions in AI agent token cost and increases in task success.
The person running the study owns the product under test. The experiment design
acknowledges this and builds in structural commitments to compensate:
pre-registration, mechanical transformations, publish-regardless, full raw data.

Phase 3 of that design requires tasks to be "adversarially reviewed by the
external reviewer before freeze," because "tasks can unconsciously drift toward
what a manifest happens to surface."

**Everything you are reviewing was produced by an AI agent** working in a single
long session, in collaboration with the product owner. That matters for what to
look for: fluent, confident, internally-consistent reasoning that is nonetheless
wrong, and claims that sound verified but were not actually checked.

## A warning about this document

This brief was written by the same agent that produced the work. It therefore
directs your attention toward problems that agent already knows exist.

**The most valuable thing you can find is something this document does not
mention.** Section 6 exists for that. If you only answer the questions in
sections 4 and 5, you will have audited the parts already under suspicion and
missed the parts nobody thought to doubt.

Prefer running things over reading claims about them. Every assertion below is
checkable, and several were wrong on first attempt during development.

## 2. What the experiment does

For each repository:

- **`base`** — the repo as published, pinned to a commit SHA
- **`twin_high`** — `base` after running `clarx init`, the product's own onboarding command
- **`twin_low`** — `twin_high` with the manifest mechanically converted to prose and
  structured markdown flattened into continuous prose

Source files are byte-identical across twins. Only documentation differs.

An agent then performs identical tasks in each twin, and token cost and success
rate are compared.

Current measured score separation:

| Repo | base | twin_high | twin_low |
|---|---:|---:|---:|
| SDEverywhere | 65 | 65 | 65 |
| gqloom | 50 | 65 | 50 |
| fuse-backend-rs | 50 | 65 | 50 |
| neocmakelsp | 50 | 65 | 50 |

## 3. Decisions taken, stated without defence

Each of these was a judgement call. The strongest argument *against* each is
given, not the argument for. Do not treat the framing as balanced — form your own.

**3.1 `twin_high` is built by running `clarx init` rather than authored by hand.**
Against: this makes the treatment "a file generated by the vendor's own tool,"
and the score improvement it produces is partly definitional, since two of the
rules that move simply check whether that file exists. A critic could call the
score gap circular.

**3.2 The information-volume guard measures only rewritten documents, not total
documentation.** The design document specifies ±15% on total documentation
volume. That was changed during implementation because restating a compact JSON
manifest as prose necessarily inflates word count, so every faithful restatement
tripped a guard meant to catch unfaithful ones. Against: this is the author
loosening a constraint that was inconvenient, which is exactly the move the
design's integrity commitments exist to prevent. The change is not yet ratified.

**3.3 Analysis should key on assignment (high vs low), not on observed score
gap.** Proposed because one repo shows a zero score gap while being genuinely
treated. Against: this decouples the analysis from the score, which is the thing
the product sells — "adopting Clarx helps" is a weaker and different claim than
"a higher Clarx score means lower cost."

**3.4 Task prompts describe behaviour and never name files.** Against: real users
often know roughly where to look, so this may overstate navigation difficulty in
both arms — and it is not obvious that it overstates it *equally*.

**3.5 Repos were selected by GitHub star range as a proxy for "not memorized from
training data."** Against: star count is a weak proxy for training-set presence,
and no direct memorization check was performed.

## 4. Specific questions

1. Read `.twins/gqloom/twin_diff.patch`. Does `twin_low` genuinely contain the
   same information as `twin_high`, or has the transformation quietly lost
   something an agent would have used?
2. Read the four tasks in `tasks/gqloom/`. Is any of them easier to *locate* in
   `twin_high` for a reason other than structure — for example, does the prompt's
   wording echo a heading that survives in one twin but not the other?
3. The prompts were written by an agent that had read the repository. Do any
   assume knowledge not derivable from the repo itself?
4. `checks/task_04.spec.ts` identifies the required helper by searching exports
   for a name matching `/pascal/i` that is not `pascalCase`. Is that gradeable, or
   can a wrong solution pass and a right one fail?
5. Is the degradation reversible in a way that matters — could an agent
   reconstruct the manifest structure from the prose cheaply enough that the
   experiment measures nothing?

## 5. Claims to verify rather than accept

Each was asserted during development. Each is checkable. At least one earlier
claim in this project turned out to be wrong when finally tested.

- "Source files are byte-identical between twins." — check the patches.
- "No pinned public repository changed score" when a scan rule was altered.
- "`clarx init` output is thin and therefore a conservative floor."
- "Every validator rule fires" — the tests claim this; confirm they test what
  they say.
- "Tasks are grounded in code read at the pinned commit, not invented." — the
  bug-fix task claims `pascalCase("_leading")` returns `"Leading"`. Run it.

## 6. Open section — the part that matters most

Sections 3 to 5 list what is already suspected. This section is for what is not.

- What would you have done differently that nobody here considered?
- What would a hostile reviewer at a conference attack first?
- Is the experiment measuring what it claims? If the result comes out positive,
  what is the most plausible explanation *other than* the hypothesis?
- Is there a cheaper study that answers the same question more convincingly?
- Should this experiment be run at all, in this form?

A conclusion of "the design is sound but answers a question not worth asking"
would be a useful finding, not a failure.
